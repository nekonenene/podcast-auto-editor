# 技術調査メモと既知の落とし穴

2026-08 の技術調査結果の要約と、実装中に判明した注意点。

## 文字起こしエンジンの選定

whisper.cpp (whisper-rs) + large-v3-turbo q5_0 をデフォルトにした。

| 候補 | 判断 | 理由 |
|---|---|---|
| whisper.cpp + large-v3-turbo | **採用** | Metal 対応で 90分→10分前後。Rust に静的リンクでき配布が最も楽。日本語の自由会話に頑健 |
| Kotoba-Whisper v2.0 (GGML) | モデル選択肢として対応 | TV音声由来の ReazonSpeech 学習でドメイン依存が強い。2026年の第三者ベンチマーク（Neosophie）では複数話者の自由会話で CER 0.495 と large-v3-turbo (0.184) に大差で劣る。公式 GGML 変換があるため whisper.cpp でそのまま動く |
| faster-whisper | 不採用 | Apple Silicon で Metal 非対応 (CPU のみ)、Python 必須 |
| mlx-whisper | 不採用 | whisper.cpp の約2倍速だが Python 同梱が必要で配布が複雑化 |

- モデルは初回利用時に Hugging Face からダウンロードし、
  `~/Library/Application Support/net.hatone.PodcastAutoEditor/models/` にキャッシュする。
  Windows は `%LOCALAPPDATA%` 配下 (data_local_dir)。574MB のモデルが
  ドメイン環境でログオン同期される Roaming (data_dir) を避けるため。
- モデル追加は `crates/pae-core/src/transcribe/model.rs` の `MODELS` に1エントリ足すだけ。

### GPU 推論

- macOS: Metal を常時有効（target 依存の feature 指定なのでビルド環境の追加要件なし）
- Windows / Linux: `cuda` feature の opt-in（要 CUDA Toolkit + NVIDIA GPU）。
  CUDA Toolkit が無い環境でもビルドできるよう、target 依存での無条件付与にはしていない。
  feature は pae-cli / pae-app → pae-core → whisper-rs へと伝播する。
  whisper.cpp は GPU ビルドならデフォルトで GPU を使うためコード変更は不要。
  feature なしでは CPU 推論になり、Apple Silicon の Metal より大幅に遅い

### whisper-rs 0.16 の既知バグ

`FullParams::set_abort_callback_safe` はクロージャを二重 Box するのに trampoline が
具象型として直接デリファレンスするため未定義動作になる（whisper_full が error -6 を返す）。
本プロジェクトでは生ポインタ API + AtomicBool で回避している
（`transcribe/mod.rs` の abort_trampoline）。whisper-rs 更新時は修正状況を確認すること。

## VAD の選定

Silero VAD (`voice_activity_detector` crate) を採用。

- MIT ライセンス、約2MB の ONNX モデルが crate に同梱（ネットワーク不要）
- 16kHz で 512 サンプル (32ms) 単位の確率を返す
- TEN VAD は精度で勝るが「Agora と競合する形での利用禁止」条項付きで不採用
- WebRTC VAD は精度不足（Silero 比エラー約4倍）

日本語の相槌（「うん」等、100〜200ms）を拾うため recall 重視のパラメータにしている:
threshold 0.4 / min_speech 100ms / min_silence 250ms / padding 前150ms・後250ms。
`min_speech_ms` を 250ms などに上げると相槌が消えるので注意。

## 無音カットの方式

`select`/`aselect` + `setpts`/`asetpts` + `aresample=async=1` による全再エンコードを採用。
映像と音声は**別々の ffmpeg プロセス**で処理し、最後に無劣化で多重化する
（理由は次節の落とし穴を参照）。

- smart cut (区間 stream copy + 境界のみ再エンコード) は高速だがグリッチ・同期ズレの
  報告が多く不採用。将来の高速化候補として温存
- カット後の PTS 振り直し（setpts=N/FRAME_RATE/TB / asetpts=N/SR/TB）が音ズレ防止の要。
  映像と音声で別プロセスに分けても、どちらもゼロから振り直すため同期は保たれる
- フィルタ式はファイル渡しにする。**ffmpeg 9 で `-filter_complex_script` は廃止**され、
  汎用の `-/filter_complex <file>` 構文に変わった
- エンコーダ: macOS は h264_videotoolbox（Media Engine、x264 比約4倍速）。
  品質は同ビットレートで x264 に劣るためビットレートを多めにしている (720p: 4M, 1080p: 6M)
- Windows は h264_mf（Media Foundation）。LGPL ビルドの ffmpeg に libx264 が入らないため。
  ビットレート表は videotoolbox 用に盛った値をそのまま流用している。
  CI の Windows ランナーにはハードウェアエンコーダが無いため、統合テストは libx264 に固定している

### カットの継ぎ目には短いフェードが要る (2026-08 に実測)

無音を詰めた継ぎ目では、部屋鳴りの波形が不連続につながってプツッというノイズになる。
実測した 16分の収録では、継ぎ目 24 箇所の隣り合うサンプルの差が中央値 58、最大 3224 あった
（16bit の振幅。周囲の部屋鳴りは 1〜2 程度）。

継ぎ目の手前へ 20ms のフェードアウトを掛けると、中央値 11・最大 2454 まで下がる。
残った大きい差は、継ぎ目のすぐ後ろにある発話の立ち上がりで、継ぎ目そのものではない。

継ぎ目の後ろにフェードインは掛けない。
段差の合計は前後に掛けたほうが小さくなる（7994 に対して 5474）が、
実際に聴くと話し始めが鈍って聞き取りにくくなる。
数字の上での滑らかさより、話し始めの明瞭さを採った。

実装で引っかかった点を4つ残しておく。

- **フェードだけ足しても効かない**。aselect も afade も音声フレーム単位でしか働かず、
  入力そのままのフレーム（AAC なら約 21ms）ではフェードの窓が継ぎ目に届かない。
  実測でも段差の合計は 11913 → 11800 とほぼ変わらなかった。
  `asetnsamples=n=256` でフレームを約 5.3ms へ組み直して初めて効く
- **継ぎ目の数だけ afade を並べると遅くなる**。フィルタが増えるほど1フレームあたりの
  処理が重くなる。16分の収録で afade 48 個なら 2.5秒だが、384 個では 45秒まで伸びた。
  そこで afade は1個だけ置き、`asendcmd` で継ぎ目ごとに設定を送り直して使い回す。
  これなら継ぎ目が何箇所あっても 1.5秒で終わる
- **asendcmd へ渡すパスは引用符とコロンのエスケープが両方要る**。
  `asendcmd=filename='C\:/path/to/cmds.txt'` の形にしないとフィルタ記述の解析に失敗する
- **フェードアウトのあと、afade の音量は 0 のままになる**。
  そのため残す区間の先頭ごとに次のフェードアウトを予約し直す形にした。
  予約の開始時刻はまだ先なので、その瞬間に音量がもとへ戻る。
  フェードインを挟まずに戻せるのはこの性質のおかげである

副次的な効果として、フレームを細かくしたぶんカットの位置が正確になり、
出力長のズレが -60ms から +5ms へ縮んだ。映像と音声を別プロセスで処理しているので、
音ズレの余地が減るという意味でも都合がよい。

### 対談収録には「長い無音」がほとんど無い (2026-08 に実測)

実際の収録 3 本の timeline.json を集計したところ、間の長さは次の分布だった。

| 収録 | 本数 | 中央値 | 90 パーセンタイル | 最長 |
| --- | --- | --- | --- | --- |
| Podcast 72分 | 380 | 640ms | 1472ms | 3072ms |
| Podcast 4分 | 67 | 832ms | 1664ms | 2336ms |
| MTG 16分 | 83 | 544ms | 1056ms | 1792ms |

複数人の会話をひとつのトラックへミックスした録音では、片方が黙るともう片方が話すため、
全員が同時に黙る時間はほとんど生まれない。
そのため秒単位のしきい値を置くと短縮がまったく働かず、短縮率が 0% になる。

VAD の誤検出を疑って ffmpeg の `silencedetect` と突き合わせたが、
72分の収録で -30dB なら 3.6分、-40dB なら 1.9分と、VAD の 2.7分は妥当な範囲に収まっていた。
VAD が無音と判定した箇所の実測音量も -33〜-50dB で、判定そのものは正しい。

なお、この素材で無音短縮によって縮められる尺は、しきい値を限界まで下げても 2% 程度が上限。
それ以上を求めるならフィラー除去など別の手段が要る。

### 落とし穴: プリセットのしきい値は「間」の長さで持つ

発話区間の前後にはパディングを付ける（初期値は前 150ms・後 250ms）。
このパディングは無音セグメントから差し引かれるため、
セグメントの長さをそのまま判定に使うと、しきい値 3000ms が実際には 3400ms の間を要求してしまう。

そこで `decide_silence` では、セグメント長にパディング分を足し戻した「耳に聞こえる間の長さ」で判定し、
残す長さも逆にパディング分を引いてから決めている。
設定値がそのまま体感の秒数になるので、プリセットを調整するときに迷わない。
パディングの合計 400ms が間の下限になる点にだけ注意する。

### 落とし穴: 長尺入力で音声が無警告に切れる (2026-08 に遭遇)

ひとつの `filter_complex` に映像出力と音声出力を同居させると、
**ffmpeg 9 は長尺の入力で音声ブランチを途中で打ち切ることがある**。
警告は出ず、終了コードも 0 のままなので、外部プロセスの成否だけでは検知できない。

96分の録画（1080p24）を72分へ編集した実例では、映像は 4332.750 秒と正しいのに
音声が 1449 秒しか書かれなかった。MP3 と文字起こしは編集後の音声を元にしているため、
そこで連鎖的に途切れた。

切り分けの結果は次のとおり。

| 条件 | 音声の長さ (期待 4332.7 秒) |
|---|---|
| 現行の1プロセス (h264_mf) | 1449.4 / 1457.6 秒 |
| `aresample=async=1` を外す | 1459.0 秒 |
| エンコーダを libx264 に替える | 1703.4 秒 |
| `-max_interleave_delta 0` を付ける | 1447.0 秒 |
| 出力ファイルを映像用・音声用に分ける | 1398.0 秒 |
| **映像と音声を別プロセスにする** | **4332.7 秒（正常）** |

- 同じフィルタ式でも、音声だけで流せば必ず完走する。フィルタ式は正しい
- 切れる位置は実行ごとに変わる。タイミング依存であり、論理バグではない
- 出力ファイルを分けても切れるので muxer の問題ではない。フィルタグラフ側の問題
- 映像エンコーダが速いほど音声が短くなる傾向がある
- `-c:v copy` の段（BGM ミックス・ラウドネス調整）では起きない。
  映像エンコーダというボトルネックが無く、音声ブランチが置いていかれないため

分割のコストはほぼ無い。映像パスと音声パスを並行して走らせると、
音声パスは映像パスの裏に隠れる。上記の実例では 324秒（壊れた1プロセス版）に対し、
分割・並列版は 242秒で、**正しくなったうえで速くなった**。

再発を検知するため、`cut_media` / `mix_bgm` / `apply_loudnorm` / `encode_mp3` の後に
出力のストリーム長を ffprobe で確かめている（`verify_output_duration`）。
許容誤差を出力長の2%と広めに取っているのは、`select` がフレーム単位、
`aselect` が音声フレーム単位で切るため、keep_ranges の数だけ丸め誤差が積み上がるから。

## FFmpeg の配布とライセンス（Phase 3 で対応）

- 開発中は PATH の ffmpeg（Homebrew 等）を使用。`PAE_FFMPEG_DIR` で上書き可能
- 配布時は **LGPL 構成の自前ビルド**を Tauri sidecar として同梱する
  - libx264 は GPL のため使わない。macOS=h264_videotoolbox / Windows=h264_mf で LGPL を維持
  - macOS arm64 の LGPL 静的バイナリを配る定番サイトは存在しないため自前ビルドが必要
    （martin-riedl.de のビルドスクリプトがベースに使える。Windows は BtbN の LGPL 版が使える）
- LGPL の義務: 対応ソースの提供、About 画面での表記
  「This software uses code of FFmpeg licensed under the LGPLv2.1」、LGPL 全文の同梱

## loudnorm

2パス (測定→linear=true で適用) で -16 LUFS (Apple Podcasts 標準) に合わせる。

- 測定 JSON は stderr の末尾に出る。他ログと混ざるため最後の `{...}` を抽出してパースする
- loudnorm は内部で 192kHz にアップサンプルするため出力に `-ar 48000` を明示する

## 聴感評価からの品質改善 (実装済み)

- **声の帯域の EQ 分離**: BGM 側だけ `equalizer=f=2500:width_type=o:w=2` で
  声の中心帯域を下げる (`voice_duck_db`, デフォルト -4dB, 0 で無効)。
  声側は加工しない
- **エンディングの BGM 余韻**: カット段階で映像の最終フレーム静止 (tpad) と
  音声の無音パディング (apad) を末尾に足し、BGM のフェードアウトを
  その余韻に重ねる (`ending_tail_s`, デフォルト5秒, BGM なしなら付かない)

## ベンチマーク実測 (M系 Apple Silicon, 2026-08)

実録画 (720p30) をフルパイプライン処理 (BGM + loudnorm + 文字起こし込み):

- 161秒入力 + large-v3-turbo: 合計 35.1s (**RTF 0.22**)。60分動画なら約13分の計算
- 内訳の傾向: 動画編集と loudnorm が各 ≈ 実時間の 6%、文字起こし (turbo) ≈ 6%、VAD ≈ 0.6%

## 話者分離の作り (2026-08)

WeSpeaker の ResNet34 を VoxCeleb で学習させたモデル (26MB) を ONNX で動かし、
発話区間ごとの声質ベクトルを求めて、指定された人数へクラスタリングしている。

| 部品 | 採用 | 理由 |
|---|---|---|
| 埋め込みモデル | wespeaker_en_voxceleb_resnet34_LM | 26MB と小さく、話者の切り分けが実測で安定していた |
| 特徴量抽出 | knf-rs (kaldi-native-fbank の Rust バインディング) | fbank の細かな作法を自前で書くと精度だけが静かに落ちるため |
| 推論 | ort 2.0.0-rc.10 | Silero VAD が引いているものと同じ版。onnxruntime が二重にリンクされない |
| 発話区間 | EditTimeline の Speech セグメント | VAD を掛け直さずに済む。純粋関数 timeline_to_speech_ranges で出力側の時刻へ写す |
| 埋め込みの単位 | 学習は1.5秒の窓、判定は0.5秒の窓 | 発話区間のままだと話者の交代をまたいで声が混ざる（次節） |

モデルは sherpa-onnx の GitHub Releases から取得している。
Hugging Face の pyannote 版は利用条件への同意が必要で、自動ダウンロードに使えない。

### CAM++ は同じ手順では動かない

同じ配布元にある wespeaker_en_voxceleb_CAM++ (29MB) を最初に試したが、
話者認識用の音声で確かめたところ、**同じ話者どうしのほうが別の話者より似ていない**結果になった。

| 組み合わせ | CAM++ | ResNet34 |
|---|---|---|
| 同じ話者 | 0.50〜0.73 | 0.62〜0.74 |
| 別の話者 | 0.46〜0.90 | 0.05〜0.36 |

原因は特徴量の正規化である。knf-rs の `compute_fbank` はフレーム方向の平均を引くところまでを含むが、
CAM++ はこれを引かない前提で学習されている。ResNet34 は引く前提なのでそのまま噛み合う。
sherpa-onnx もモデルごとにこの正規化の有無を切り替えている。

埋め込みモデルを差し替えるときは、
**同じ話者の別録音どうしが、別の話者より確実に似ること**を先に確かめること。
ここが逆転していても処理は最後まで通ってしまい、後段をいくら調整しても当たらない。

### 発話区間をそのまま埋め込むと壊れる (2026-08 に実測)

当初は発話区間ひとつからベクトルをひとつ求めていたが、これでは実収録で使い物にならなかった。

発話区間は 250ms 未満の無音でつながり、さらに前後へ 150ms / 250ms のパディングが乗る。
つまり**間が 400ms を切ると、別の話者の発話がひとつの区間に融合する**。
対談の間の長さは中央値が 544〜832ms なので、分布の下のほうは確実にこれを下回る。

2秒ずつ交互に話者が入れ替わり、間が 200ms しかない音声で確かめたところ、
8ターンが6区間へ融合し、**6区間のうち5つを同じ話者と誤判定**した。
混ざったベクトルは、その区間を外すだけでなくクラスタの重心そのものを濁らせるため、
周りの正しいはずの区間まで巻き添えにする。

さらに厄介なことに、このとき重心との距離の差 (margin) は 0.30〜0.58 と**大きいままだった**。
重心が壊れている状態では、確信度の指標は当てにならない。

対策として、発話区間を窓へ切り分けてから埋め込みを取る。
同じ音声で 18窓すべて正解、5分へ引き伸ばした音声でも 322窓すべて正解になった。

### 窓の長さは「学ぶ」ときと「判定する」ときで変える (2026-08 に実測)

窓を 1.5秒でそろえると、今度は**長い発言に挟まった短い発言が拾えない**。
0.6秒の割り込みは 1.5秒の窓の中で多数派になれず、周りの話者へ飲まれてしまう。
実測でも、4回仕込んだ割り込みのうち検出できたのは1回だけだった。

かといって窓を短くすると、今度は埋め込みが不安定でクラスタが作れない。
そこで**学習と判定で窓の長さを分けた**。

| 段 | 窓 | ずらす幅 | ねらい |
|---|---|---|---|
| 話者を学ぶ | 1.5秒 | 0.75秒 | 重心を作る。長さを優先する |
| 話者を判定する | 0.5秒 | 0.25秒 | 短い発言を拾う。できあがった重心と比べるだけなので短くてよい |

短い埋め込みは**クラスタを作るには弱いが、できた重心と比べるには使える**。
これで割り込みの検出が 1/4 から 3/4 へ改善した。
残る1件は VAD が発話として拾っておらず、話者分離より手前の取りこぼしだった。

学習側の重なりをやめると 5分の音声で 4秒しか速くならないのに、
重心が粗くなって話者不明が 186個から 235個へ増えたため、重なりは残している。

### 判定は「近さ」だけでなく「差」も見る

短い窓は音の情報が少ないぶん重心から離れやすく、
長い窓に合わせた距離のしきい値 0.55 では判定の半分を捨ててしまった。
5分の音声で測った最短距離は中央値 0.554、90%点 0.795 で、0.75 が妥当だった。

| しきい値 | ラベル付与 | うち誤り | 見送り |
|---|---|---|---|
| 0.55 | 490 | 0 | 494 |
| 0.75 | 800 | 1 | 184 |
| なし | 984 | 35 | 0 |

さらに、距離が近くても**どちらの話者からも同じくらいの距離**なら当てずっぽうになる。
実測した誤りの差は 0.002 / 0.002 / 0.016 / 0.016 / 0.071 / 0.136 に集中していたので、
差が 0.02 を下回る窓は話者を決めないことにした。
5個の判定を諦めるだけで、誤りが6件から2件へ減った。

文字起こしのセグメントへは、重なり時間の多数決で写す。

### 判定のしきい値

- 400ms 未満の窓はクラスタリングへ参加させない。日本語の相槌はこの長さを下回ることが多く、
  埋め込みが安定しないまま混ぜるとクラスタの重心が濁る
- 重心からコサイン距離 0.75 より離れた窓は「話者不明」にする。
  `dev diarize` は窓ごとの距離と margin を JSON へ出し、`--max-distance` でこの値を変えて試せる。
  収録ごとに変える値ではないため、GUI や config.toml へは出していない
- whisper のセグメントへは重なり時間の多数決で写す。
  最多の話者が6割に届かなければ「話者不明」にする

### 文字起こしの音声はカット直後から取る

以前は BGM と loudnorm まで済ませた完成品から音声を取り出していたが、
BGM が乗った音声は話者の声質を濁らせるため、カット直後の中間ファイルから取るようにした。
`mix_bgm` も `loudnorm` も尺を変えないので、タイムスタンプは完成品と一致したままになる。
